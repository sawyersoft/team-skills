# 改进代码库架构
本指令旨在发现架构中的摩擦点，并提出把模块做深（deepening opportunities）的重构方案——即通过重构将“浅层模块”转化为“深层模块”，从而提升代码的可测试性与 AI 导航效率。

该命令的实施须基于项目的领域模型，并统一使用以下设计词汇表：
- 调用 Skill 工具的 `codebase-design` 获取架构词汇表（**包括 module/模块**、**interface/接口**、**depth/深度**、**seam/接缝**、**adapter/适配器**、**leverage/杠杆率**、**locality/局部性**）及其核心原则（如删除测试、“接口即测试表面”、“单适配器等于伪接缝，双适配器才是真接缝”）。在所有建议中必须精准使用这些术语，切勿漂移使用“组件（component）”、“服务（service）”、“API”或“边界（boundary）”等词汇。
- 良好的接缝命名应参考 `CONTEXT.md` 中的领域语言和术语；重构方案不可推翻 docs/adr/ 中已记录的架构决策。

## 执行流程

### 1. 探索阶段 (Explore)

**扫描前先明确范围：坚持 YAGNI 原则（非必要不添加）。** 把模块做深（Deepening）的收益在于降低其未来的改动成本，因此应将重点放在近期变动频繁的代码上。在开始扫描前，先决定**在哪里**寻找机会：
- 如果用户已经明确指出了方向（某个特定模块、子系统或痛点），则直接进入该方向，跳过下述推导步骤。
- 否则，拉取一段足够长的提交历史（git log --oneline），找出代码库中的“热点地区”（即频繁出现的文件和区域），并将注意力优先集中在这些路径上。如果改动非常零碎、没有明显的聚集点，再扩大扫描范围。

在动手前，首先阅读项目在该区域的领域术语表（`CONTEXT.md`）以及相关的架构决策记录（ADRs）。

随后，派生一个子智能体使用去有机地、非机械地探索代码库，并记录下你在哪些地方体验到了“摩擦力”，切勿遵循僵化的启发式规则：
- 哪些地方为了理解一个概念，需要在多个零碎的浅层模块之间反复跳转？
- 哪些模块过于**浅显（shallow）** ——接口的复杂度几乎等同于其内部实现？
- 哪些纯函数虽然为了方便测试而被抽离，但真正的 Bug 其实隐藏在它们的调用方式中（缺乏**局部性/locality**）？
- 哪些紧密耦合的模块将其内部实现穿透到了接缝（seams）之外？
- 代码库的哪些部分目前缺乏测试，或者很难通过现有的接口进行测试？

对怀疑是浅层模块的代码进行**删除测试（deletion test）**：如果直接删掉它，复杂度是会在一个核心地方消灭掉，还是只是平移到了别处？如果答案是“会在核心地方消灭”，这就是你需要抓取的重构信号。

### 2. 以 HTML 报告形式呈现候选方案 (Present candidates as an HTML report)

在系统的临时目录中生成一个独立的 HTML 文件（以防临时文件污染代码仓库）。从 `$TMPDIR` 获取临时目录路径，若不存在则降级使用 `/tmp`（Windows 系统下使用 `%TEMP%`）。文件名命名为 `<tmpdir>/architecture-review-<timestamp>.html` 以确保每次运行都是一个独立的新文件。为用户自动打开该文件（Linux 使用 `xdg-open <path>`，macOS 使用 `open <path>`，Windows 使用 `start <path>`），并告知用户该文件的绝对路径。

报告使用 **Tailwind via CDN** 进行布局与样式设计。在展示图表、调用链路、依赖关系或时序结构时，使用 **Mermaid via CDN** 生成图表。允许将 Mermaid 与手写的 CSS/SVG 视觉元素混用：关系呈图状时（如调用图、依赖树、时序图）使用 Mermaid；需要更具表现力的视觉呈现时（如体量图、剖面图、折叠动画），使用手写 Div 或 SVG。每个候选方案都必须包含 **Before/After（重构前/后）的视觉对比**。报告必须保持高度的视觉化。

针对每个候选方案，渲染一张包含以下内容的卡片：

- **涉及文件 (Files)**：涉及哪些文件或模块。
- **当前痛点 (Problem)**：为什么现有的架构正在引发摩擦。
- **解决方案 (Solution)**：用通俗易懂的语言描述重构后将发生什么改变。
- **预期收益 (Benefits)**：从局部性（locality）和杠杆率（leverage）的角度进行阐述，并说明测试将得到改善。
- **前/后对比图 (Before / After diagram)**：左右并排、自定义绘制，直观展现当前的“浅显性”以及重构后的“深度”。
- **推荐指数 (Recommendation strength)**：分为 Strong（强烈推荐）、Worth exploring（值得探索）、Speculative（纯属推测） 三档，以标签形式渲染。

报告的结尾须包含首选推荐 (Top recommendation) 章节：指出你认为最应该优先治理的是哪个方案，并说明理由。

**必须使用` CONTEXT.md` 中的词汇来描述领域业务，使用 /codebase-design 中的词汇来描述架构。** 如果 `CONTEXT.md` 中定义了 “Order（订单）”，应表述为“订单接收模块（Order intake module）”，而不是 “FooBarHandler” 或 “Order service（订单服务）”。

**ADR 冲突处理**：如果某个候选方案与现有的 ADR 相冲突，只有当该处的架构摩擦大到足以合理推翻既定 ADR 时才允许将其列出。同时必须在卡片中清晰标记（例如带有警告高亮：_“该方案与 ADR-0007 冲突，但仍值得重新讨论，因为……”_）。切勿将 ADR 所禁止的每一种理论上的重构可能都罗列出来。

完整的 HTML 脚手架、图表模式和样式指南参见[HTML-REPORT.md](HTML-REPORT.md)。

**在此阶段切勿直接提出具体的接口设计。** 文件写入完成后，向用户询问：“您想深入探索其中哪一个方案？”

### 3. 灵魂烤问循环 (Grilling loop)

一旦用户选定了一个候选方案，调用 `grilling` 这个 Skill 工具与用户一起梳理整个决策树：包括边界约束、依赖关系、深层模块的具体轮廓、隐藏在接缝（seam）背后的逻辑、以及哪些既有测试应该保留。

随着决策的逐步固化，在线触发相应的副作用。调用 `domain-modeling-context`这个 Skill 工具以保持领域模型的实时同步：

- **重构后的深层模块引入了 CONTEXT.md 中不存在的新概念？** 立即将该术语添加至 `CONTEXT.md`（若文件不存在则延迟创建）。
- **在对话过程中理清了原本模糊的术语？** 立即更新 `CONTEXT.md`。
- **用户由于某些关键且合理的架构原因拒绝了该方案？** 主动提出为其记录 ADR，话术为：_“需要我将此记录为一项 ADR 吗？这样可以避免未来的架构评审再次提出相同的重构建议。”_ 仅在拒绝理由具有长期参考价值、能防止后人踩坑时才提出此项建议；若是由于临时性原因（如“当前维护周期内不划算”）或显而易见的原因，则无需记录。
- **需要为重构后的模块探索不同的接口设计？** 调用 `codebase-design` 这个 Skill 工具，并启动其 `design-it-twice`（设计两次）的并行子智能体模式。
