# ADR Format
ADR（Architecture Decision Record，架构决策记录）统一存放在 `docs/adr/` 并且 文件名采用**date + slug** 的格式，slug：用于简洁描述主题的短标识，通常使用小写英文和连字符，例如 use-event-driven-messaging，文件名最终的名称形式如：: `2026-08-18-use-event-driven-messaging.md`, `2026-08-19-use-event-driven-messaging.md` 等。

docs/adr/ 目录采用**按需创建（lazy creation）**的方式：只有在确实需要创建第一个 ADR 时，才创建 docs/adr/ 目录。

## 模版

```md
# {简短的决策标题}

{用 1～3 句话说明决策背景、最终决定了什么，以及为什么做出这个决定。}
```

仅此而已。一个 ADR 完全可以只有一个段落，ADR 的价值在于记录：做出了什么决策，以及为什么做出这个决策。而不是为了形式完整而堆砌各种章节。也就是说：ADR 的重点是“Decision + Why”，而不是“文档结构”。

## 可选章节

仅在确实能带来实质价值时才纳入这些章节。大多数 ADR 并不需要它们。
- Status 前置元数据（proposed | accepted | deprecated | superseded by ADR-NNNN）——在决策被重新审视时有用
- Considered Options——仅当被否决的备选方案值得被记住时
- Consequences——仅当需要指出非显而易见的下游影响时

## 什么时候应该建议创建 ADR（When to offer an ADR）

必须同时满足以下三个条件，才应该建议创建 ADR：

1. **难以逆转（Hard to reverse）** — 未来改变这个决定需要付出明显的成本。
2. **没有背景信息会让人感到意外（Surprising without context）** — 未来的开发人员看到代码时，很可能会产生：“为什么这里居然要这么做？”
3. **是经过真实权衡后的结果（The result of a real trade-off）** — 当时存在多个合理的替代方案，经过比较后，基于明确原因选择了其中一个。

如果一个决定很容易改变，那以后直接改掉即可；如果这个决定并不令人意外，未来也没人会问为什么；如果根本不存在真正的替代方案，那么除了“我们按最自然的方式做了”之外，也没有什么值得记录的。

### 哪些决策值得记录
- **架构形态。** “我们采用 monorepo。” 或者 “写模型采用事件溯源，读模型直接读取到MySQL。”
上下文之间的集成模式。 “Ordering 与 Billing 通过领域事件通信，而非同步 HTTP。”
带来锁定效应的技术选型。 数据库、消息总线、认证提供方、部署目标。并非每一个库——仅限那些更换需要一个季度的选项。
边界与范围决策。 “Customer 数据由 Customer 上下文拥有；其他上下文仅通过 ID 引用。”明确的“否”与明确的“是”同等重要。
对显而易见路径的刻意偏离。 “我们因 X 原因使用手动 SQL 而非 ORM。”任何合理读者会默认相反做法的情况。这些记录能阻止下一位工程师去“修正”本为刻意为之的设计。
代码中不可见的约束。 “因合规要求我们不能使用 AWS。”“因合作方 API 契约，响应时间必须低于 200ms。”
被否决且否决理由非显而易见的备选方案。 若你考虑过 GraphQL 却因微妙理由选择了 REST，请记录下来——否则六个月后就会有人再次提议 GraphQL。
