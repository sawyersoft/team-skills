# 领域建模

在设计过程中，应当**主动构建并持续完善项目的领域模型**。这是一项需要*主动*介入的工作 — 不仅要识别和质疑术语，更要主动设计能够验证领域边界的边界场景（Edge Cases），并在术语或决策真正明确下来后，立即将其记录到**术语表（Glossary）和决策记录（Decisions）**中。这个 Skill 真正价值责任是：当领域模型发生变化、被澄清或被重新定义时，主动参与建模，而不是仅仅被动消费已有的上下文信息。

这个 Skill 主要形成这样一个闭环：
发现模糊 → 质疑术语 → 明确概念 → 用边界场景验证 → 与代码交叉验证 → 确认领域语言 → 立即更新 CONTEXT.md → 必要时记录 ADR

其中尤其要区分两个文件的职责：
- CONTEXT.md 职责为What：领域里有哪些概念，以及这些概念究竟是什么意思
- ADR 职责为Why：为什么在多个可行方案中选择了这个方案

因此，`CONTEXT.md` 更接近 领域语言/术语的事实来源（Source of Truth），而 ADR 是架构决策的历史记录。两者不要混在一起。

## 文件结构
大多数代码仓库只有一个领域上下文（Context）：
```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果项目根目录存在 CONTEXT-MAP.md，则说明该仓库包含多个领域限界上下文（Bounded Context）。CONTEXT-MAP.md 会指出每个上下文对应的 CONTEXT.md 所在位置：
```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 订单上下文专属决策，针对订单这个特定领域范围内上下文决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/				  ← 账单上下文专属决策，针对账单这个特定领域范围内上下文决策
```

按需创建文件（Create files lazily）—— 只有在确实有内容需要记录时才创建文件。如果不存在 `CONTEXT.md`，那么在首次确定一个领域术语的正式含义时创建它。如果不存在 `docs/adr/`，那么在首次需要记录 ADR 时创建它。

## 在会话过程中如何工作（During the session）

### 对齐现有术语表 (Challenge against the glossary)
当用户使用的术语与现有 `CONTEXT.md` 中定义的领域语言发生冲突时，应当立即指出这一冲突。例如：“你的术语表将 cancellation 定义为 X，但从你当前的表述来看，你似乎指的是 Y。请确认这里具体采用哪一种含义？”

这里的重点不是纠正用户的英语单词，而是维护项目的 Ubiquitous Language（通用语言），确保同一个领域概念在整个团队和系统中具有一致、明确的含义。

### 消除模糊语言
当用户使用含义模糊、范围过宽或者存在多个领域含义的术语时，应主动提出一个更加精确的规范术语（Canonical Term）, 例如：“您刚才提到了‘账户（account）’：请问您是指‘客户（Customer）’还是‘用户（User）’？这两个是完全不同的概念。”

这里几个概念需要特别理解：
Fuzzy language（模糊语言）：一个词的边界不清晰，无法准确判断它代表什么领域概念。
Overloaded term（重载术语）：同一个词在不同语境下代表不同概念。
Canonical term（规范术语/标准术语）：项目最终确定下来、作为领域语言统一使用的正式名称。
Ubiquitous Language（通用语言）：DDD 中非常核心的概念，即业务专家、开发人员以及系统模型共同使用的一套明确且一致的领域语言。

### 使用具体场景讨论领域概念
当讨论领域对象之间的关系时，应通过具体业务场景对模型进行压力测试（Stress Test）。主动设计一些能够触及**边界条件（Edge Cases）**的场景，迫使参与者明确不同概念之间的边界和关系。

例如，不要只讨论：“Order 和 OrderItem 是什么关系？” 而应该进一步提出：
- “如果一个订单包含 3 个商品，只取消其中 1 个商品，这算是订单取消还是订单部分取消？”
- “如果订单中的最后一个商品被取消，订单本身是否自动进入取消状态？”
- “如果订单已经发货，还允许取消商品吗？”

这些具体场景能够帮助我们确认领域模型中概念的边界、生命周期和状态转换规则。

### 与代码交叉验证（Cross-reference with code）
当用户描述某个领域行为或业务规则时，应检查代码实现是否与其一致。如果发现矛盾，应直接指出：“你的代码实现的是整个 Order 的取消，但你刚才说支持部分取消。究竟哪一种才是正确的领域规则？”

这里的 Cross-reference with code（与代码交叉验证） 非常重要：领域模型不是只存在于文档里的抽象概念，还必须与实际代码所表达的行为保持一致。

### 即时更新 CONTEXT.md
当术语一经确认，立即更新 `CONTEXT.md`。切勿将这些更新攒到最后批量处理，务必在发生的瞬间将其捕获。更新格式须严格遵循[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。这里强调的是即时更新（inline update）。

`CONTEXT.md `必须完全剥离任何具体的技术实现细节。切勿将 CONTEXT.md 当作需求规格说明书、草稿纸或记录实现决策的仓库。**它有且仅有一个身份：领域术语表。**

### 克制地提出 ADR 记录请求 (Offer ADRs sparingly)
仅在以下三点同时成立时，才提议创建 ADR：
1. **难以逆转** —— 日后改变决定的代价显著，例如可能需要重构，或较大的修改。
2. **缺乏上下文则令人费解** —— 未来读者会疑惑“为何如此设计？”
3. **源于真实权衡** —— 存在切实的备选方案，并基于具体理由做出选择，例如：PostgreSQL 和 MySQL 都可以满足需求，但最终因为某些明确的业务或技术原因选择 PostgreSQL。这才属于真正的 Trade-off（权衡）。

若三点中有任何一点不成立，则跳过 ADR。格式遵循 [ADR-FORMAT.md](./ADR-FORMAT.md)。
