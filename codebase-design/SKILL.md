# 代码库设计

设计**深模块（Deep Module）**：保持interface简洁，把行为逻辑封装在application服务层或domain层，并以清晰的界面（Seam）进行封装，确保可通过该接口进行测试。在设计或重构代码的任何环节都应遵循这种语言和原则。其目标是为调用者提供便利，为维护者提供局部性，并为所有人提供可测试性。

## 术语表（Glossary）
必须严格使用以下术语，不要用其他词替代：**不要用 `component`、`service` 或 `API` 来替代这些术语，也不要用 `boundary` 表示这里的 Seam。** 保持术语的一致性至关重要。

### 模块（Module）
**模块（Module）**：任何具有**接口（Interface）**和**实现（Implementation）**的代码单元，都可以称为模块。模块不受规模限制：一个函数、一个类、一个包，甚至一个跨越多个层次的完整功能切片，都可以是模块。
*避免使用*：单元（Unit）、组件（Component）、服务（Service）。
这里的关键是：Module并不等于某一种固定的代码结构，它只是“拥有接口和实现的东西”，因此，一个函数可以是 Module，一个完整的分层功能也可以是 Module。

需要根据上下文来区分“模块”这个词的具体意义，是指Java 9中引入的module模块（JPMS）；还是指代码代码块；又或者是业务领域模块。如果上下文无法明确“模块”这个词的具体含义时需要跟用户确认。

### 接口（Interface）
**接口（Interface）**是指调用方为了正确使用一个 Module，**必须了解的全部信息**。
接口不仅包括类型签名，还包括：
- 约束条件：调用方必须满足哪些前置条件。
- 调用顺序：操作是否有特定的先后顺序。
- 错误处理：可能出现哪些错误，以及错误如何表现。
- 配置要求：使用模块之前需要提供哪些配置。
- 性能特征：调用成本、延迟、资源消耗等特性。

**避免使用：** API、签名（Signature）。

原因是 API 通常指对外暴露的编程接口，而签名只涵盖类型层面的定义，都不足以表达调用方实际需要了解的全部信息。

### 实现（Implementation）

**实现 (Implementation)**：指模块内部的具体内容，即代码主体，这与**适配器 (Adapter)** 概念不同：一个事物既可以是“小适配器配大实现”（如 Postgres 仓储），也可以是“大适配器配小实现”（如内存模拟实现）。
适配器强调的是某个对象在设计中的角色，而实现强调的是模块内部具体包含什么。

总之，当你在讨论代码之间的“对接缝隙（seam）”、代码使用接口（interface）或 “解耦切面”时，请用“适配器（Adapter）”这个词；而当你在讨论模块内部的具体代码逻辑时，用“实现（Implementation）”才更准确。

### 深度（Depth）
深度衡量的是：调用方通过一个接口，能够获得多少能力，以及为此需要理解多少接口信息。
当模块以简洁的接口封装了大量行为时，它就是一个深模块。
当模块的接口与内部实现一样复杂，调用方仍然需要了解大量细节时，它就是一个浅模块。

### 接缝（Seam）
经典著作《修改代码的艺术》（Working Effectively with Legacy Code）作者 Michael Feathers 提出的标志性概念 —— Seam（接缝）。
“接缝（Seam）”指的是代码里这样一个神奇的地方：你不需要改动这里的代码，就能直接改变它的运行行为。它就是模块接口所处的那条“交界线”，也就是 **模块(Module)的 接口（Interface）所处的位置。**
因此，在架构设计时Interface 代表的 Seam 应该放在哪里本身就是独立的设计决策，而“它背后的具体实现怎么写代码”则是另一回事，两者不能混为一谈。

*避免使用*：边界（`boundary`），因为 边界（`boundary`） 在 DDD 中已经经常用于 **限界上下文（Bounded Context）**，容易产生概念冲突，容易鸡同鸭讲。

### 适配器（Adapter）
所谓的“适配器（Adapter）”，就是卡在“接缝（Seam）”上刚好能实现某个 Interface 的具体对象。Adapter描述的是它在设计中承担的“角色”（看它填补了哪个空缺），而不是它的内部实现。也就是说：Adapter 关注的是“它承担了哪个接口的实现角色”，而不是“它内部采用了什么实现方式”。

### 杠杆效应（Leverage）
杠杆效应是调用方从模块深度中获得的收益。调用方只要学习一个Interface，就能获得到成倍的功能。
一个实现可以通过统一的接口服务于多个调用方和测试场景。实现一次，就能在 N 个调用点和 M 个测试中复用其能力，而不必重复实现相同逻辑。
因此： **一个好的深模块，用较小的 Interface 换取较大的实现能力。**

### 局部性（Locality）
局部性是模块深度给维护者带来的收益。变更、缺陷、知识和验证都集中在一个地方，而不是分散在各个调用者之间。一次修复，处处有效。

# 深模块 vs 浅模块

## 深模块（Deep Module）

**小 Interface + 大量 Implementation**

```text
┌─────────────────────┐
│      小型接口       │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深层实现       │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

核心思想：**把复杂度藏在模块内部，让调用方只面对一个简单的 Interface。**深模块通过少量接口暴露丰富的能力，将复杂逻辑隐藏在内部，调用方无须了解实现细节，就能完成复杂操作。

## 浅模块（Shallow Module）
**大型 Interface + 少量 Implementation**
```text
┌─────────────────────────────────┐
│          大型接口               │  ← 方法多，参数复杂
├─────────────────────────────────┤
│          薄层实现               │  ← 主要只是透传
└─────────────────────────────────┘
```

这种设计应该尽量避免。

典型表现是：每一层都只是简单地把参数往下一层传递，却增加了新的 Interface、类型和调用关系。这种情况下，新增的模块没有真正隐藏复杂度，因此属于浅模块。
设计一个 Interface 时，应主动问：
- 能不能减少方法数量？
- 能不能简化参数？
- 能不能把更多复杂度隐藏在模块内部？

核心目标不是：“Interface 看起来足够完整”，而是：**让调用方用尽可能小的认知成本获得尽可能大的能力。**

# 核心原则（Principles）

## 1. 深度取决于接口（Interface），而不是实现（Implementation）
模块的深度取决于其接口，而不是内部实现有多复杂。
一个深模块的内部完全可以由多个小型、可模拟、可替换的部分组成，只要这些部分不暴露给模块的调用方，就不会因此削弱模块的深度。
模块既可以有供调用方使用的外部接缝（External Seam外部替换点），也可以有仅供内部实现及其测试使用的内部接缝(Internal Seam内部替换点)。

因此：内部可以很复杂、很模块化；对外仍然应该保持一个简单的 Interface。

## 2. 删除测试（The Deletion Test）
尝试设想：如果删除这个模块，会发生什么？
- 如果删除后，相关复杂性也随之消失，说明这个模块可能只是一个简单的转发层，没有真正创造价值。
- 如果删除后，原本封装的复杂性重新分散到 N 个调用方中，说明这个模块确实发挥了作用。

这个测试可以帮助判断：一个模块是否真正封装了复杂性，而不是仅仅增加了一层间接调用。

## 3. 接口就是测试面（The Interface Is the Test Surface）
调用方和测试代码应该穿过**同一个 Interface**与模块（Module）交互。如果为了测试一个 Module，不得不绕过它的 Interface，直接测试它内部的实现，那么这个 Module 很可能设计得不对，理想状态是：调用方怎么使用，测试就怎么使用。

## 4. 一个适配器只是潜在的替换点，两个适配器意味着真实的替换需求
如果一个Interface只有一个实现Adapter，那这个“Interface接缝”纯粹是你凭空想象出来的需求；当一个interface至少接了两个不同的适配器时，这条接缝才算真正立住了。只要某个业务还没有出现真正的“多变性”，就千万别为了解耦而留Interface。
**不要为了抽象而抽象。只有当替换点两侧确实存在差异时，才值得引入这一抽象。**

### “一个适配器 = 伪需求”
- 很多程序员在写代码时，喜欢搞“防御性设计”。比如明明系统只用到了 Mysql 数据库，他非要定义一个 IUserRepo 接口，然后写一个 MysqlUserRepo 去实现它。他心里想的是：“万一以后要换 Oracle 呢？”
我们要直接戳破这个幻想。如果代码里，某个接口（Seam interface）永远只有唯一一个真实实现（One adapter），那这个接口就是纯纯的摆设。你只是在为你脑补出来的“伪需求”买单。

### “两个适配器 = 真需求” (Two adapters means a real one)
什么时候这个接口才真正有价值？至少有两种情况（Two adapters）：
- 线上 vs 测试： 线上跑的是真实的 PostgresAdapter，跑单测时换成了内存里的 In-MemoryFakeAdapter。
- 业务多态：比如支付场景，底下同时接了 AlipayAdapter 和 WechatAdapter。

只有当你真正把两个不同的东西插进同一个槽里时，你才算没有白挖这个槽。

### 终极戒律：没有变化，就别加戏 (Don't introduce a seam...)
- 增加一个接口/接缝是有代价的。它会增加系统的认知成本、让代码跳转变得更麻烦（Ctrl+左键点进去只能看到接口，还要再点一步看具体实现）。
- 架构师的克制：优秀的架构师应该遵循 YAGNI 原则（You Aren't Gonna Need It —— 你根本不需要它）。在变化真正发生之前，保持代码的简单和直接；当第二种情况真的出现时，再去重构出interface。

# 面向可测试性进行设计
优秀的 Interface 应该让测试变得自然。

## 1. 接收依赖，不创建依赖
```java
// GOOD 易于测试
public void processOrder(order, paymentGateway) {}

// BAD 难以测试
public void function processOrder(order) {
  StripeGateway gateway = new StripeGateway();
}
```

第一种方式将依赖交给调用方提供，便于在测试中替换为模拟对象或测试适配器。
第二种方式在函数内部直接创建具体依赖，使测试更难隔离外部系统，也降低了实现的可替换性。

## 2. 返回结果，而不是直接产生副作用

```java
// GOOD 易于测试
public Discount calculateDiscount(cart){
  return new Discount();
}

// BAD 难以测试
public void calculateDiscount(cart) {
  cart.total -= discount;
}
```

第一种方式将折扣计算与外部状态修改分离，测试时只需验证输入和输出。
第二种方式直接修改购物车状态，测试还需要处理状态变化及其带来的影响。
这里强调的是设计方向：尽可能将可计算的逻辑设计为明确的输入与输出，将副作用控制在必要的位置。

## 3. 保持 Interface 足够小：
接口方法越少，通常需要编写和维护的测试就越少；参数越少，测试准备工作就越简单。
在满足实际需求的前提下，应尽可能减少接口暴露的方法、参数和使用约束。

# 概念之间的关系
- 一个模块（Module）恰好有一个接口（Interface），该接口是调用方和测试代码使用它时所面对的统一契约。
- 深度（Depth）描述模块相对于其接口所提供的能力。
- 替换点/接缝（Seam）是模块接口所在的位置。
- 适配器（Adapter）位于 seam（替换点/接缝）上，通过实现接口来接入模块。
- 深度带来杠杆效应（Leverage），让调用方以更低的理解成本获得更多能力。
- 深度带来局部性（Locality），让维护者可以集中处理变更、缺陷和验证工作。
- **Depth** 为调用方带来 **Leverage**，为维护者带来 **Locality**。

整体关系可以概括为：简洁的接口 → 更深的模块 → 更高的复用收益与更好的维护局部性。

# 被否决的观点（Rejected Framings）

## 1. 不用实现代码行数与接口代码行数之比衡量深度
单纯按照代码行数计算，会鼓励人为增加 Implementation 的代码量，从而制造虚假的“深度”，我们禁止采用这种定义，而是采用深度杠杆效应来衡量深度。
这里采用的标准是：**调用方通过接口实际获得了多少能力，以及需要为此付出多少理解成本。**

## 2. 不把接口局限于编程语言中的 `Interface` 关键字或类的公开方法
这里的 **接口** 并不特指：开发语言 的 `interface` 关键字,也不只是一个 Class 的 public methods，这种理解太狭窄，而是 **调用方为了正确使用这个 模块(Module)，必须了解的所有事实信息，包括类型定义、约束条件、调用顺序、错误处理、配置要求和性能特征。**

## 3. 不使用“边界（Boundary）”代替“接缝/替换点（Seam）”
不要使用 `边界（boundary）` 来描述这里的接缝替换点，因为`边界(boundary)` 在 DDD 中已经与 **Bounded Context（限界上下文）** 紧密相关。为了避免与 DDD 概念混淆，这套术语统一使用：**接缝或替换点（Seam）** 或 **接口（Interface）** 而不是 `边界`。

# 进一步深入

## 深化现有模块
参考 `DEEPENING.md` 里的指南，分析模块的深化机会，重点关注：
- 依赖的分类与处理。
- 严守接缝替换点的设计纪律。
- 通过`替换实现而不是叠加封装`来进行测试。

## 探索不同的 接口 设计方案
参考 `DESIGN-IT-TWICE.md` 指南通过并行子代理，以几种差异明显的方式设计同一个接口，然后从以下维度进行比较：
- 深度（Depth）：接口能提供多少能力。
- 局部性（Locality）：变更与维护是否集中。
- 替换点位置（Seam Placement）：接口设置的位置是否合理。

最后拉出来PK，从“深度（是否以小博大）”、“高内聚性”以及“接缝位置（扩建点留得准不准）”这三个维度进行全方位比对。
