# 模块深化（Deepening）
在明确依赖关系的前提下，如何安全地将一组浅模块重构为深模块。采用 SKILL.md 中定义的术语：模块（Module）、接口（Interface）、接缝或替换点（Seam）、适配器（Adapter）。

## 依赖分类
在评估一个模块是否适合进一步深化时，首先要对它的依赖进行分类。依赖属于哪一类，会直接决定：深化后的 module 应该如何跨 接缝或替换点的接口 进行测试。

### 1. 进程内（In-process）
纯计算、内存状态、无 I/O。这类依赖始终可以进行深化，直接合并这些浅模块，并通过新的 Interface 对深化后的 模块（Module） 进行测试，无需额外引入 Adapter。

### 2. 本地可替代（Local-substitutable）
拥有本地测试替身的依赖（如 Postgres 的 PGLite、内存文件系统），如果已经存在可靠的本地替代实现，那么这类依赖也可以进行深化。
在测试套件中启动相应的替代实现，并使用它测试深化后的模块。此时接缝或替换点（seam）替换点保留在模块内部，对于调用方而言，这个内部 接缝的接口 应该是不可见的，不需要在模块的外部接口上额外定义端口（Port）。

### 3. 远程但自有（Ports & Adapters）
通过网络进行交互、但由自己控制的服务，例如微服务和内部 API。
这种情况下应在接缝(seam)处定义一个**接口**，生产环境提供 Adapter，测试环境提供 Mock Adapter。
如果是DDD结构项目，接缝接口和对应的Adapter应放在infrastructure/adapter目录中。

Adapter实现服务调用统一使用 **service-sdk** 依赖包中封装的服务接口，如果这个依赖中没有找到有关接口时需要更新 **service-sdk** 增加相关的接缝实现。

### 4. 真正外部（Mock）
这一类指的是你无法控制的第三方服务（例如：Stripe、alipay、WeChatPay 等），深化后的 module 应该把该外部依赖作为一个注入的 interface，业务使用时提供实例Adapter，测试时提供一个 Mock Adapter。
核心原则是：第三方服务的不可控性应该被隔离在 Adapter 后面，而不是泄漏到 Deep Module 的业务逻辑中。

## 接缝/替换点的设计纪律（Seam Discipline）
1. 一个适配器意味着潜在的替换点，两个适配器意味着真实的替换需求
不要在没有实际替换需求的情况下引入端口(port接口)。通常，至少需要有两个合理的适配器，才值得设置这样的替换点，例如：生产环境使用的真实实现，测试环境使用的替代实现。

2. 区分内部替换点与外部替换点
深模块既可以拥有内部替换点，也可以拥有外部替换点。
- 内部替换点： 仅存在于模块实现内部，供模块自身的测试使用。
- 外部替换点： 位于模块对外提供的接口处，供调用方使用。

内部 Seam 则属于 Implementation 私有结构，可能只用于：
- 内部依赖替换
- Module 自身测试
- 局部实现隔离（外部 接缝替换点位于模块的的Interface上）。

不要因为测试代码会使用内部 替换点（seam），就把它暴露到模块的外部 Interface 中，也就是说，测试需要替换某个内部依赖，并不意味着调用方也需要知道这个依赖。

## 测试策略：替换，而非叠加
- 当新的 深化后模块 已经能够通过它的接口被完整测试后，旧浅模块上的单元测试通常就已经失去价值，应当删除它们。
- 在加深后的模块接口上编写新测试。**调用方如何使用这个 Module，测试就应该如何测试这个 Module。
- 测试通过接口断言可观察结果，而非内部状态，核心原则：测试行为，而不是实现。
- 测试应该能够经受内部重构，因为测试描述行为而不是实现，只要接口没有变化测试就不应该修改。若实现变更时测试也必须修改，则说明它越过了接口进行测试。
