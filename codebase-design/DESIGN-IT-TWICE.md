# 设计两次（Design It Twice）
当用户希望针对某个已经选定的**深化候选模块（Deepening Candidate）**探索不同的 Interface 设计方案时，使用这里定义的并行 Sub-agent 模式。这一方法基于 Ousterhout 提出的 Design It Twice 思想：你的第一个设计方案通常不会是最好的方案。这个模式通过 “强制分身”，逼迫 AI 在动手前必须交出至少 3 份截然不同的设计方案，通过“左右互搏”来榨出最高 Leverage（杠杆率） 的接口。

本流程沿用 SKILL.md 中定义的统一术语：Module（模块）、Interface（接口）、Seam（接缝）、Adapter（适配器）、Leverage（杠杆）。

## 流程

### 1. 界定问题空间
- **你在干什么：** 
这时候你是总指挥（主 Agent），你先别急着写具体代码而是先把战场清理干净，在启动 Sub-agent 之前向用户说明当前候选模块所处的问题空间（Problem Space），告诉用户和接下来的子智能体：“我们今天要在哪里动刀子”。

- **核心输出：**
1. 套上紧箍咒（Constraints）： 这个接口必须满足那些约束条件（比如：必须在 50ms 内响应、必须支持高并发异步等）。
2. 摸清朋友圈（Dependencies）： 梳理它依赖谁，并根据 `DEEPENING.md` 进行分类（例如：是跟数据库死磕的重型依赖，还是纯内存计算的轻量依赖）。
3. 画个草图或伪代码（Code sketch）：提供一份伪代码出来。注意：这只是为了把规矩具象化，绝对不是最终方案！ 

将这些内容直接展示给用户，然后**立即进入第 2 步**，不需要等待用户再次确认，这样设计的目的是：用户可以一边阅读并思考问题空间，多个 Sub-agent 同时在后台并行探索不同设计方向。

### 2. 并行启动多个 Sub-agent
使用 Agent 工具并行启动至少 3 个 Sub-agent。每个 Sub-agent 都必须针对同一个待深化 Module，提出明显不同、甚至方向截然不同的 Interface 设计，防止它们互相抄袭。

为每个子代理提供独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后放置的内容）。该简报与第 1 步中面向用户的问题空间说明相互独立。为每个代理赋予不同的设计约束：
- 代理 1（极简主义者）：目标是 “以小博大（Depth）” 的极致。最小化interface，整个接口只能有 1 到 3 个方法，里面却能吞掉排山倒海的复杂度。
- 代理 2（变形金刚）：目标是 “极致灵活性”。配置要足，扩展性要强，能应付未来 72 变，支持多种用例和扩展。”
- 代理 3（傻瓜相机）：目标是 “最常用的场景一键直达”。让 90% 的普通调用者连脑子都不用动，默认配置就能跑得极爽。
- 代理 4（乐高大师，可选）：专门针对跨边界的复杂依赖，设计 ports、gateway 和 adapters。”

在简报中同时纳入 [SKILL.md](SKILL.md) 术语表（Glossary）与 [CONTEXT.md](CONTEXT.md) 词汇，使每个子代理在命名上与架构语言及项目领域语言保持一致。
每个子代理输出：
1. Interface接口（类型、方法、参数，以及不变量、调用顺序、错误模式）。
2. 展示调用方如何使用的示例，用于判断 这个设计对调用方来说究竟有多简单或者多复杂。
3. 接缝背后的实现隐藏了什么，用于判断 Module 是否真的具有足够的 Depth。
4. 依赖strategy与adapters（见 [DEEPENING.md](DEEPENING.md)）。
5. 权衡，明确指出哪些地方 Leverage 很高，哪些地方比较薄，每个设计都应该明确说明：它在哪些方面更强，又在哪些方面主动做了哪些妥协。

### 3. PK 并给出推荐（Present and compare）
按顺序逐一展示设计方案，包括它们的接口长啥样、调用示例、在 Seam（接缝） 后面藏了什么脏活、以及各自的优缺点。

然后用自然语言进行横向 PK 比较：
- **Depth（深度）**：谁的接口性价比最高？Interface 提供了多少 Leverage，调用方需要学习多少内容；Module 隐藏了多少复杂行为；Interface 是否明显小于其背后的 Implementation。
- **Locality（局部性）**： 谁能让以后的改动缩在局部，不外溢？一个好的设计应该尽可能集中在 Module 内部，而不是扩散到大量调用方。
- **Seam placement（接缝位置）**： 谁的插槽挖得最精妙，最方便以后拔插和写测试？Interface 究竟应该位于哪里，也就是：哪些内容应该放在 Seam 里面；哪些变化应该被隔离在 Seam 外面；Seam 是否放在了真正存在变化的位置上；Seam 的位置与 Interface 的内容是两个不同的设计问题。

最后给出明确推荐：
主 Agent 必须像一个资深架构师一样，给出极其坚定、有明确倾向性的最终结论。如果不同设计中的元素可以很好地融合，请提出一个“混合方案（Hybrid）”。要有自己的观点：用户想要的是引人入胜的阅读体验，而不是菜单。
